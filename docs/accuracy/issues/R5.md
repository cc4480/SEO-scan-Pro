## New defects

### N-R5-01 Link prober reports "404" from a HEAD request without confirming with GET
- Site / finding: 27-notion, critical 2 and fix 8 ("two internal links return HTTP 404").
- Symptom: https://www.notion.so/product/features and /product/demos are reported as broken crawl-equity leaks. They work: GET returns 301 -> https://www.notion.com/product/features, then 200 (same for demos). Only HEAD returns 404.
- Evidence: `curl -I` -> 404, `curl` (GET, plain and with a Chrome UA) -> 301/200 (follow gives 200). Scan log: "links warn 404 https://www.notion.so/product/features".
- Root cause: `lib/crawler.ts` ~537-545: the GET fallback only runs for 405, 501 and 403; a 404/410 from HEAD is trusted.
- Proposed fix: when HEAD answers 404, 410 or >=500, repeat as GET (and follow redirects) and count the link broken only if GET agrees. Regression test with a mock server that 404s HEAD and 200s GET.
- Related: none (new class).

### N-R5-02 The scanner's own browser identity is wrong for some sites and right for others; no fallback
- Site / finding: 28-canva (all), 26-stackoverflow (simulated), 30-w3c (ground side).
- Symptom: Chromium is launched with the UA "Mozilla/5.0 (Windows NT 10.0; Win64; x64) SEO-Scan-Pro/1.1" (`lib/crawler.ts:9`). It has no engine token, so Canva answers 200 "Unsupported client - Canva" (reproduced with curl: that UA and "compatible; SEOScanPro" give the 10 KB interstitial, Chrome/130 or Safari 17 UAs give the real 470 KB page, bare "Mozilla/5.0", curl and all bot UAs give a Cloudflare 403 challenge). On Stack Overflow the same UA does not pass the Cloudflare challenge on /questions (403 "Just a moment...") although the real-Chrome UA does. Conversely w3.org challenges every Chrome-looking UA (my curl and puppeteer with Chrome/130 or 124 stuck on "Just a moment...") and serves the real page to the SEO-Scan-Pro UA, so simply switching to a Chrome UA would break W3C.
- Evidence: curl and puppeteer runs listed in the sheets for 28 and 30; ground (Chrome/124 UA) got the real Canva page and the W3C challenge.
- Root cause: single fixed UA, no detection of "I was served a refusal page" followed by a retry.
- Proposed fix: after render, detect an interstitial/challenge (title "Unsupported client", "Just a moment", "Attention Required", "Access Denied", Cf-Mitigated header, tiny DOM with noindex) and retry once with the other identity (Chrome-token UA <-> SEO-Scan-Pro UA); if the retry is clean, use it and say which identity was used. Also wait for a JS challenge to clear before judging (Stack Overflow's real browser passes it). Only if both fail, report "could not be audited" (never audit the interstitial).
- Related: A-03 (this is the producer side; A-03's pageKind detection is the consumer side).

### N-R5-03 The raw (no-JavaScript) fetch is a different transport and gets bot challenges; the report concludes "JS-dependent"
- Site / finding: 30-w3c criticals 1 and 3 and fix 6 (false), 28-canva fix 14 (false).
- Symptom: W3C: rawStatus 403, 5.6 KB, 9 words, 0 links versus 774/89 rendered, so the report says the homepage is JavaScript-dependent and invisible to non-JS crawlers (high-priority fix). Real raw HTML (curl with the scanner UA) is 200, 775 words, 96 links; W3C is fully server-rendered. Canva: raw is the 755 KB 403 challenge page (32 words, 99 links of challenge markup) compared with the 58-word interstitial, "rawLinks 99 vs renderedLinks 6" (real raw: 1245 words, 404 links).
- Evidence: curl bodies saved in scratch (`Cf-Mitigated: challenge` header on W3C; `challenge_title` markup on Canva); node fetch with a Chrome UA gets 403 where curl with the same UA gets 200 (Cloudflare also fingerprints the TLS client).
- Root cause: `lib/audit/collect.ts` ~37 fetches with `BROWSER_UA` (Linux Chrome/124) through `safeFetch`; a 4xx raw response, or one carrying challenge markers, is still compared with the rendered DOM; `rawVsRendered` and the contradiction/scoring code do not check `rawStatus`.
- Proposed fix: if rawStatus >= 400 or the body looks like a challenge/interstitial, mark rawVsRendered as "not measured" (no JS-dependence finding, no score penalty, no "raw 403" sentence), or retry the raw fetch with the identity that worked for the render (N-R5-02). Add a unit test with a challenge-like raw response.
- Related: A-10 (raw numbers), A-03, N-R5-02.

### N-R5-04 Executive summary says the interstitial was "HTTP 403" although the render was 200
- Site / finding: 28-canva, executive summary and criticals 1-3.
- Symptom: "served an interstitial 'Unsupported client' page (HTTP 403, ...)". The rendered page status was 200; the 403 belonged to the raw fetch (a different page, the Cloudflare challenge).
- Evidence: mainPage.status 200, facts.rawVsRendered.rawStatus 403, scan log "render ok HTTP 200".
- Root cause: the model is given both statuses without saying which belongs to which page (`lib/deepseek.ts` payload) and nothing re-checks status wording.
- Proposed fix: with A-03, if pageKind is 'challenge' replace the whole report body with a deterministic "the site served a bot/browser-check page" notice; otherwise label each status with its source.
- Related: A-03, N-R5-03.

### N-R5-05 Simulated (placeholder) reports: fabricated findings, inconsistent disclosure, fabricated agent prompt
- Site / finding: 26-stackoverflow 1-10, 29-tesla 2-13.
- Symptom: with `isSimulated`, the model is still sent the placeholder payload (brand "Stackoverflow"/"Www" from the host name, title "<Brand> | Leading Solutions & Professional Services", 14 images/3 without alt, 28 links/19 internal, H2 "Frequently Asked Questions", JSON-LD Organization/WebSite/LocalBusiness, 58 KB/529 ms, load time called "fast") and writes findings, fixes, aeoAssessment (richSnippetEligibility lists the fake types), competitor text and an agentReadyPrompt (tasks "add alt text to the 3 images", "rewrite the meta title" for a coding agent) from it. Scores are the same for both sites (68/72/65/70/85). Tesla's first critical states the data is simulated, Stack Overflow's finding list never does (only the executive summary), so the same situation is displayed two ways.
- Evidence: results/26 and results/29 `crawl.mainPage` (isSimulated true, placeholder values), `report.criticalIssues`, `report.agentReadyPrompt`; ground shows the real Stack Overflow page (1549 words, 155 internal links, 19 images, no FAQ) and Tesla "Access Denied".
- Root cause: `lib/crawler.ts` placeholder generator feeds `lib/deepseek.ts` as if it were data; `finalize.ts` has no simulated mode.
- Proposed fix: when simulated, skip the model; return exactly one deterministic finding ("The site could not be read: <reason>, no audit was performed"), no scores (or null), empty fixes/aeo/competitor text, and an agent prompt that says nothing could be audited. Probe-derived items that were actually read (none here) may stay. Test: simulated crawl -> report contains no placeholder strings ("Leading Solutions", "Frequently Asked Questions", "LocalBusiness").
- Related: A-04 (this is its full scope), A-01.

### N-R5-06 A 403 first response is treated as "no usable content" even when the page then renders
- Site / finding: 26-stackoverflow (whole scan).
- Symptom: the main document answered 302 -> /questions -> 403 (Cloudflare "Just a moment..." JS challenge). Ground truth's Chromium (Chrome UA) passes it and ends on the real page (status recorded as 403 from the first response, 1549 words), so "unreachable" is a scanner limitation, and the user is told the site could not be reached.
- Evidence: curl of /questions with any of the three UAs -> 403 "Just a moment..."; puppeteer with Chrome UA -> final title "Newest Questions - Stack Overflow".
- Root cause: `lib/crawler.ts` decides simulate-or-not from the first main-document status and the DOM captured at network idle, with no wait for a managed challenge to clear.
- Proposed fix: if the title/body matches a known challenge, wait (poll up to ~10 s) for navigation to a non-challenge page; judge the final DOM, not the first status; reword the message from "unreachable" to "blocked by a bot check". Related: N-R5-02, A-03.

### N-R5-07 Raw field names and code identifiers leak into user-facing text
- Site / finding: 27-notion 3, 9 and 4 (`robotsTxtAllows`, `structuredData.hasJsonLd`, `missingAltCount`), 26/29 (`sitemapFound: false`, `llmsTxtFound: false`), 28 (`meta.canonical`, `visibleSections.faq`, `genuineReviewsVisible`), 30 (`sitemapFound false`).
- Symptom: findings read like JSON paths, not sentences.
- Root cause: prompt payload field names are quoted by the model; no sanitiser in `finalize.ts`.
- Proposed fix: instruct the model not to quote field names and strip/replace known identifiers in the finalizer. Cosmetic.
- Related: none.

### N-R5-08 "Fix" entries that the report itself says are not defects (padding)

- Related: A-13, A-05.

### N-R5-09 (ground-truth tool, lead-owned) challenge pages are not detected; the sheet flags and "mismatch" labels follow
- Site: 28-canva (JS-off 31 words/1 link: the challenge), 30-w3c (every rendered measure: title "Just a moment...", H2 2, 1 image), 28/30 bot rows labelled MISMATCH when scanner and ground both read 403 ("refused vs baseline" rule in review.ts).

- Related: A-12.
